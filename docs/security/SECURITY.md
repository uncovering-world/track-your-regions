# SECURITY.md

## OWASP ASVS Target Level: 2

We target ASVS Level 2 (standard security for apps handling personal data).
Level 1 requirements are mandatory. Level 2 requirements are expected.
Level 3 requirements are tracked but optional for now.

## Application Profile

- **Type**: Web application (travel/region tracking with user accounts)
- **Auth**: Email/password + Google OAuth 2.0 (Apple Sign-In planned)
- **Data sensitivity**: User travel history, visited regions, location preferences
- **APIs**:
  - REST API (Express). Public read endpoint: `GET /api/world-views/regions/:regionId/members/descendant-geometries` (optionalAuth, publicReadLimiter)
  - REST API. `GET /api/experiences/points` (#910, ADR-0061) is the widest anonymous read the
    product has: one request answers every reader-visible place of the catalogue — thousands
    of coordinates (8 842 on 2026-09-22), or their names, kinds and types when a box narrows it. No
    `optionalAuth`, because like `/search` and `/:id/finds` it names only what any reader may
    open and answers the same to everyone, so there is no caller-shaped body to keep out of a
    cache. What bounds it is `publicReadLimiter` — a per-IP ceiling a deployment sets,
    `RATE_LIMIT_PUBLIC_READ_MAX`, defaulting to 60/min rather than fixed at it — a 20 000-row cap on the
    read itself — `bbox` is optional on both tiers, and a limiter bounds how often a stranger
    asks rather than what each ask costs — and the four reader-facing predicates every other
    reader-facing read composes (`db/membership.ts`,
    `db/readerPredicates.ts`), each negative-tested against live rows.
    A read that hits the cap says `truncated: true` rather than answering with part of the
    world in silence.
    It makes the published catalogue cheaper to enumerate than paging an object list would,
    which is a scraping and capacity cost rather than a disclosure: the data is what this
    product exists to publish. It is deliberately *not* a Martin tile source, which would have
    put the same rows on an unauthenticated port with no limiter at all — see § Known Gaps on
    the tile server, and ADR-0061 for the rest of why.
  - Internal CV microservice (FastAPI, Python 3.12, port 8000). Routes: `POST /pipeline/phase1`, `/pipeline/phase2`, `/pipeline/match`, `/pipeline/respond/{review_id}`, `GET /health`. **Internal-only** — reachable only from the Node backend over the Docker bridge network; no CORSMiddleware; not exposed externally
- **File handling**: Server-side image downloads from Wikimedia (Node side; the World Heritage portal's photographs are no longer read, ADR-0043). cv-python accepts curator-submitted map images via multipart upload (`UploadFile`) for the OCR/clustering pipeline; it processes the bytes in memory, never writes them to disk under user-controlled names. An admin's reference map for the Create Subregions dialog is uploaded to the Node backend as a data URL (`PUT /api/world-views/regions/:regionId/image-overlay`, admin only, #595): PNG, JPEG or WebP checked by signature, at most 10 MB, kept as `bytea` in the database (ADR-0113) and read back by admins only — an SVG is refused. The dialog's groups go through `PUT /api/world-views/regions/:regionId/subdivision-groups` (admin only): a member row is stored only when it belongs to that region, a group's child region only when it is one, so a body cannot assign another region's members
- **Frontend**: MapLibre GL (WebGL) map rendering, SPA with React + MUI
- **Sessions**: JWT access tokens (15min, in-memory) + refresh tokens (httpOnly cookie, hashed in DB). What a sign-in answers is declared as a schema (`backend/src/api/responses/auth.ts`, ADR-0066): the access token and the public account, never the refresh token, a hash or a provider id, and the parse outside production refuses any other key
- **Roles**: user, curator (scope-based), admin
- **Curator scope over a place**: a curator scoped to a source reaches a place as a whole (its name, picture, coordinate, points, works and history) when the place holds a membership of that source, whichever source first brought it (#1893, `curatorPlaceScopeExists` in `backend/src/middleware/auth.ts`, and `checkCuratorScope` for its region assignments and rejections); an answer about one membership is the scope of the membership the writer answers, named or picked as the writer picks it (`answeredSourceId`), and a type edit is the scope of the shown membership it writes; a choice between sources' views needs every source of the place (`resolveEverySourceScope`). The place's first source (`experiences.source_id`) decides no scope, and the backend lint refuses a comparison with it (`provenance/no-first-source-key`)

## Trust Boundaries

- **Browser ↔ Node backend** — public boundary. All standard ASVS hardening applies.
- **Node backend ↔ OpenAI** — the model is an untrusted execution surface, and stored operator text (a world view's `source`/`description`) reaches it. Treated as a boundary: that text is data, never instruction. With web search enabled the model also holds a tool, so injected text could otherwise redirect an outbound fetch.
- **Node backend ↔ Jev (TypeSafe)** — [ADR-0087](../decisions/0087-jev-suggests-an-answer-on-a-curator-card-and-a-curator-decides.md); optional (`JEV_API_KEY`, unset by default; a secret in the environment, never logged). `services/jev/jevClient.ts` sends one closed `choice` question per field of the sources card (#1260): the place's name and countries, each source's kind and name, and per view its text, its picture's file name and photographer, or its coordinate — catalogue data, never anything about a curator or a traveller — with `userAgent()`, a 15 s timeout, over HTTPS. The answer is untrusted: an option outside those given is refused, and an accepted one is only shown, beside the views, as a suggestion; nothing applies it. Asked by `POST /api/experiences/:id/view-suggestions` (`requireAuth + requireCurator` in every source's scope, `authenticatedLimiter`), once per field for the views as they stand, so a card opened again costs nothing, and not at all when the place's sources, read with the views, differ from the ones the scope was checked over. The *Where is it?* card asks `POST /api/experiences/:id/point-hint-suggestions` (`requireAuth + requireCurator` in the scope of a source that places the points, as the component-items card's, `authenticatedLimiter`, #1913): one call per card with a `choice` question per hint not yet judged — the site's name and countries, the component's name, reference, coordinate and why it is rough, the hint's source, label, coordinate, distance and an OpenStreetMap object's telling tags — catalogue data only, shown beside the hint and never applied. The component-items card asks `POST /api/experiences/:id/component-item-suggestions` (`requireAuth + requireCurator` in the scope of a source that places the points, `authenticatedLimiter`, #1272): one call per card with a `choice` question per candidate not yet judged as it stands — the site's name and countries, the component's name, reference and coordinate, the candidate's item, label and coordinate, the distance, the name similarity and the rule that found it; catalogue data, nothing about a person — and a 429 or 529 is backed off from once, for a named delay of at most five seconds, never longer inside a curator's request. Each answer is only shown beside the candidate; nothing applies it. The near-places card asks `POST /api/experiences/:id/merge-proposal-suggestions` (`requireAuth + requireCurator` in the scope of a source of either place of an open pair, `authenticatedLimiter`, #1249) the same way: one call per card with a `choice` question per pair not yet judged as it stands — both places' names, kinds, Wikidata items and countries, the distance, the name similarity, whether the names are the same and the reach; catalogue data, nothing about a person. Each answer is only shown beside the pair; nothing merges on it. An arriving place's card asks `POST /api/experiences/:id/visit-suggestion` (`requireAuth + requireCurator` in the scope of an arriving membership's source, `authenticatedLimiter`, #1768) for a place with an open arrival only: one call with one `choice` question — the place's name, countries and kinds, the map's tag and the lead of its English Wikipedia article; catalogue data, nothing about a person. The lead is read for the question from English Wikipedia's fixed API endpoint, with only the title taken from the stored article URL (`enwikiTitleOf`, which refuses any other host), under `userAgent()`, in one ask of at most five seconds that is never retried. Each answer is only shown on the card; nothing refuses or publishes on it. A kind's run asks the same question, with the same data, of a place it offers that fewer than two visit witnesses vouch for (#1770, `services/sync/visit/visitQuestions.ts`), and writes a curator's question where Jev reads nothing to visit there; it refuses nothing. What the calls cost, for every card, is `GET /api/admin/jev/usage` (admin).
- **Node backend ↔ cv-python** — private Docker bridge. cv-python has no auth; trust derives from network isolation. Anyone with intra-network access could call cv-python directly. ASVS L2 considers this defence-in-depth — adequate for the current threat model but documented as a known limitation; if cv-python ever moves out of the bridge or onto a shared cluster, a shared-secret header or mTLS becomes mandatory.
- **cv-python ↔ external services** — none. cv-python is sandboxed at the network level (only Wikimedia downloads happen on the Node side).

## Current Security Stack

| Layer | Implementation |
|-------|---------------|
| Password hashing | bcryptjs, 12 salt rounds |
| JWT | jsonwebtoken, HS256 only, iss/aud claims, 15min access + rotated refresh with family tracking |
| Auth middleware | requireAuth, requireAdmin, requireCurator, optionalAuth |
| Curator directory and activity | `/api/admin/curators`, `/:userId/activity` and the feed across curators, `/api/admin/curation-activity` (#611), require an authenticated admin; the feed's filters are validated (an action from the log's vocabulary, row ids within `integer`, ISO instants) and bound as parameters. The directory includes admins without assignments (#905); their displayed global scope comes from their role, creates no assignment, and has no revoke action. Real assignments remain independently revocable. |
| World view visibility | Two mechanisms. A route's declared `scope`, which the registry checks with `isVisibleToReaders` (`backend/src/middleware/worldViewVisibility.ts`) after the caller and the input are known (ADR-0071), gates the region/experience-by-region read surface by `world_views.is_public`, answering 404 (not 403) for a hidden or nonexistent world view. `getWorldViews` filters the world view listing the same way. `GET /api/experiences/:id` can't use that guard — the experience itself is public data, only its world-view association is sensitive — so it filters the `regions[]` array it returns instead, using the same predicate. Admins bypass all three. That array carries a **second** filter on a different axis since #521: a region is named only where the object has a point there that this caller may see, so an assignment a gated run made on an unread point does not disclose the region it landed in (ADR-0025 decision 5 has placement write such points into `experience_regions` deliberately). Admins bypass that one too, but they are not alone: it is relaxed on `maySeeUnreadExperience`, so a curator whose scope reaches the object is served the whole array — a curator reading a queue item has to be shown where publishing will put it. A manual assignment is exempt from it, having been made by a curator rather than derived from a point. `GET /api/experiences/:id/treasures` widens on the same boolean and, for that caller only, names the museums each work hangs in (`venues`, `venuesSql`): every venue the source places the work in, a refused or unread one included, and one outside the curator's own regions included. That is intended and bounded: the curator may already correct the work from this museum (`PATCH /:id/works/:treasureId/edit`), the correction writes the one row all of those venues carry, and the dialog has to say which museums that is before Save. What is disclosed is each venue's name, kind and source id and whether readers see the work there, and nothing else about it; a reader's row carries `venues: null` and the count alone. The review queue's cards carry the same list, behind `requireCurator`. `GET /api/experiences/search` returns the same array since #592, for the same reason and on stricter terms: that route deliberately carries no session, so it filters to `is_public` world views for **every** caller with no admin bypass, and applies the #521 point-visibility predicate unrelaxed — a search row is a link a reader clicks, and a region it could not open is not an answer ([ADR-0042](../decisions/0042-a-search-answers-about-the-catalogue-and-opens-where-the-reader-is.md)). See [world-views.md](../tech/world-views.md). Beyond the filtering itself: because the listing's rows depend on the caller, the response is marked `private, no-cache` with `Vary: Origin, Authorization` — by `optionalAuth`, as every caller-shaped read is (see the Headers row) — so it cannot be shared-cached and served to the wrong one. The client counterpart is in `useNavigation`: the listing is cached per identity, and when the visible list changes a selection absent from it is replaced, the address rewritten, and the selected region, division and breadcrumbs cleared — with Discover's own trail going with it, since #644 has Discover derive its trail from the same region rather than keeping one of its own, so a world view that stops being visible cannot stay on screen in either mode. Since #644 the world view, the region and the open card are all in the **address** (`/wv/5/r/6737-europe/e/1234-stonehenge`, [ADR-0034](../decisions/0034-a-place-has-an-address.md)), which changes what a URL can be used to ask and answers it the same way: every id in an address is restored through the reads above and no others, so a URL naming a hidden world view, a region of one, or an experience this caller may not see gets exactly the 404 those reads give — and the app then degrades to the nearest visible place silently, with no error surface and no distinction between "does not exist" and "not for you". A URL carries no personal state (no visited rows, no user ids), since addresses travel through referers, logs and chat. |
| Validation | Zod schemas on all routes (body, query, params): a declared route's own schemas, parsed after its caller is established so a refused caller never learns what its input should have been (ADR-0071). A declared path's `:name` segments must be named by its params schema, or it does not compile. A query parameter the route does not declare is refused with 400, a route that declares no query included (`strictQueryOf`, `backend/src/api/route.ts`, #1099); the one route held to no query schema is `/auth/google/callback`, whose query Google writes on its redirect and passport reads, and which says so with `foreignQuery`, a declaration the registry refuses without a reason or beside a declared query. SSE endpoints include `token` in query schema to preserve JWT for auth |
| Error answers | A failure answers a sentence written for the reader, and the error itself goes to the server log. `errorHandler` masks a 5xx in production. A handler that catches its own failure writes the sentence itself. `ERROR_TEXT_RULES` (`backend/eslint.config.mjs`) fails the lint on an error's `.message`, or `String(err)` (an error read by its name), in a response body, a redirect's address, a stream's event or a progress status (#1021). The OAuth callbacks redirect only with one of the strategies' own refusals (`OAUTH_REFUSALS`, `backend/src/auth/strategies/oauthRefusals.ts`) or "Authentication failed": never a thrown error's text, and never a provider's `error_description`, which passport-oauth2 hands over as `info.message` and which whoever sends the callback request controls. A cause the reader can act on is named by a code (`quota_exceeded`), or thrown as a `ReaderFacingError`, whose message is a sentence the product wrote and `sentenceFor` passes through. A value read into a variable before it is sent is beyond the rule. Catalogue Checks says whether a check's query failed or timed out (`couldNotRun`), never the driver's text |
| Stored picture urls | Two columns hold a url that later reaches an `<img src>`, and both are held to an allowlist on both sides. On the way in, the rule is declared once (`backend/src/types/urlSafety.ts`) and put to the URL parser rather than matched against the raw string: a link is an absolute http(s) url; a picture is a file on one of the hosts licensed to this product — `PICTURE_HOSTS` in `@tyr/shared/pictures`, the two Wikimedia Commons hosts, the one list the drawing side imports too (ADR-0065), under `/wikipedia/commons/` on the upload host, with a file name that names a picture and not the `/wiki/File:` page about one, which answers HTML (ADR-0043) — or a path whose origin survives resolution (`/images/…`, for a file we host). A curator's `image_url`, `websiteUrl` and `wikipediaUrl` read it (#693), and so do the four writers a request schema never sees, each at the point it writes: the sync upsert, the works writer and the picture repairs (`writeFoundPicture`, reached from the admin panel's *Fix pictures* for either source) hold the run's rule, `isCommonsPictureUrl`, which admits no local path; publishing a held proposal holds the curator's, `isDisplayablePictureUrl`. A region's imported map and its candidates in an admin's import tree, the map-image pick and the vision-match url hold the *link* rule instead, `isStorableHttpUrl` — any absolute http(s) url, since no map is a path on our own origin (#694), so a map from an untrusted host or a `.pdf` is stored and refused only where it is drawn — and where it is *fetched*: the two readers that fetch a picture from the server rather than draw it, the CV colour-match pipeline's read of a region's map (`runSourceMapPipeline`) and the admin image proxy (`GET /api/admin/image-proxy`), go through `fetchPicture` (`services/pictureFetch.ts`) and call the address `pictureFetchUrl` builds, never the value they were handed (#706) — an origin of ours per host in `PICTURE_HOSTS`, matched host for host, with the value's path under it segment by segment and its query after a `?` of ours, so a tree node or a query string naming `127.0.0.1`, a port or a `user@` is refused before any request leaves, where the proxy used to take any `*.wikimedia.org` / `*.wikipedia.org` by suffix and the pipeline took anything. The rule binds **every hop, not only the first**: redirects are taken by hand (`redirect: 'manual'`, at most five), each `Location` is put to the same rule and rebuilt by it before it is requested, and a chain that leaves those hosts ends in `null` rather than in bytes — which matters because the proxy hands the final bytes to its caller. A hop may also land on `thumb.wikimedia.org`, where Commons itself serves a picture it has to scale (`?width=800`, measured 2026-09-19 and re-runnable with the `curl` recorded in `urlSafety.ts` — a file narrower than the width asked for comes from `upload` instead, so a small test file does not show that host at all); a value handed in may never start there. `urlSafety.test.ts` holds that neither reader calls `fetch` itself and that every `fetch(` in `fetchPicture` — counted in any shape — takes the rule's answer, and `pictureFetch.test.ts` holds the chain, the refusal of a hop off those hosts and the hop ceiling; each of those used to be `z.string().url()`, which is `new URL()` in a try/catch and accepts `javascript:` and `data:`. Where a picture is drawn, `extractImageUrl` / `toThumbnailUrl` (`frontend/src/utils/imageUrl.ts`) decide again, and keep only an absolute http(s) url on a trusted host — a Commons host, under `/wikipedia/commons/` on `upload.wikimedia.org` — naming a picture file and not a `/wiki/File:` description page, or an `/images/` path on our own origin; both lists are the one declaration the storing side imports too (`@tyr/shared/pictures`, ADR-0065). Load-bearing rather than a second copy, because a sync writes `image_url` through no request schema and the rows already stored predate the write-path rule. `urlSafety.test.ts` pins the behaviour, that the protocol is named in no other backend module, and, by reading every frontend component, that no `src` — a JSX `src={…}` or an imperative `img.src = …`, looked at through one binding — names a stored picture raw or sizes one by hand |
| Stored link urls | Two stored links are held to the rule on **both** sides. A region's source page, `region_import_state.source_url`, is posted in an admin's import tree and by the review's add-child and rename routes (#703): on the way in, the three schemas read `isStorableHttpUrl` — an absolute http(s) url and nothing else, stored as the parser read it — where each used to be `z.string().url()`. An experience's website and Wikipedia article, `metadata.website` and `metadata.wikipediaUrl` (served to a review card as `website_url` / `wikipedia_url`), are held to the same rule when a curator writes them — the row above — and to nothing when a sync does, so every surface that offers them decides again (#708). Where either is offered, `safeHref` (`frontend/src/utils/safeHref.ts`, lifted out of `ImageCreditLine`, which asks it for a credit's licence and details links) decides, and a refused value gets no link: a glyph not drawn, a button disabled or left out (Discover's detail panel and the Map mode card show no Wikipedia or Website button for it), a title in plain text, a review card's link not named. React neutralises a `javascript:` href of its own accord (the click throws) but says nothing about `data:` or `blob:` and nothing at all about `window.open`, which the CV match review handed the stored value; the decision is the app's rather than borrowed from the framework. `urlSafety.test.ts` pins the three schemas and, by reading every frontend module (`.ts` and `.tsx`) that carries a stored link (`sourceUrl`, a credit's `licenseUrl` / `detailsUrl`, an experience's `website` / `wikipediaUrl` / `website_url` / `wikipedia_url`), that no dynamic `href={…}`, `window.open(…)` or `.href = …` assignment in such a module reaches the sink as anything but a `safeHref(…)` call or a url the file spells itself (a literal, or a template opening on `https://`) — `safeHref(x) \|\| x` counts as raw — looked at through one binding, with a name the file binds to nothing counting as raw, since the value reaches a link through a prop as often as directly |
| Database access | Parameterized `pool.query()` everywhere, typed by row interfaces generated from the schema (`backend/src/db/schema.generated.ts`); no ORM (ADR-0064) |
| Headers | Helmet (CSP, X-Frame-Options, etc.), plus cache control on every response whose body is shaped by the caller: `optionalAuth` (`backend/src/middleware/auth.ts`) sends `Cache-Control: private, no-cache` and appends `Authorization` to `Vary` on each response it lets through, because Express's default ETag + `Vary: Origin` says nothing about who asked and would let a proxy, or a future CDN, store one caller's answer under the URL alone and hand it to the next — an admin's world view list with the unpublished ones in it, a curator's region list with its rejected rows, a reader's own `is_new`. The rule sits on the middleware that puts the identity on the request rather than on each route (#597, after #460 had put it on the listing alone), so it reaches the world view listing, the `optionalAuth` experience reads and every read with a declared `scope` — where an admin gets 200 for a hidden world view and everyone else 404 — and a read added tomorrow carries it by its declaration's `optional` access and `revalidate` policy. A declared route holds that by construction, since a handler on a `public` route is told nothing about who is calling (ADR-0071). `private` is what forbids the shared cache. `no-cache` rather than `no-store` is deliberate: these bodies hold nothing the checklist classifies as sensitive (V14.2.1), and the browser's revalidation round-trip is worth keeping — a region's list, its locations and its geometry all answer `304` to a conditional request, some 865 kB gzipped for Europe that `no-store` would re-download on every reload — while the origin answers each revalidation for the *current* caller, so a stored variant is never served to the wrong one. That round-trip is unconditional for an anonymous reader and bounded for a signed-in one: `Vary: Authorization` keys whatever private cache does store it on the caller, which makes a stored variant selectable only under the token it was stored with, and the access token rotates every 15 minutes — so they get the `304` within one token's lifetime and a full body on the first read after each refresh. `res.vary` appends, where `setHeader('Vary', …)` would clobber the `Origin` CORS put there. `requireAuth` is the other half of the rule, with the other value (#710): every response it fronts — everything under `/api/users/me`, `GET /api/auth/me`, every read behind `requireAdmin` and `requireCurator` — carries `Cache-Control: private, no-store` and the same `Vary: Authorization`. Those bodies are the caller's own — a traveller's visited regions, experiences, locations and viewed works, a profile with its email, an admin's import tree — what V14.2.1 classifies as sensitive, and the exposure is the other cache: a shared one is already kept out by RFC 9111 § 3.5, since the access token travels in `Authorization`, but the browser's private cache stored the body under Express's defaults (an ETag, no freshness) and served it back on `304` after sign-out, on whatever machine the traveller had signed in from. `no-store` costs nothing there — an id list, a profile — where it would cost `optionalAuth`'s reads their round-trip. The header goes on ahead of the token check, so a 401 carries it too; a route that needs something else declares it (ADR-0071), and the registry sets it after the middleware, where `setHeader` replaces. Four admin image endpoints do: the water crop, cluster preview and cluster highlight declare `{ maxAge: 300 }` (`private, max-age=300`), the image proxy `{ maxAge: 86400, shared: reason }` (`public, max-age=86400`). The registry writes a lifetime onto the answer alone: until the handler has answered, those routes say `private, no-store`, so an upstream's 502 is never kept for a day. All four are fetched with the header, so `Vary` keys each browser entry on the token. For the three review images — read through the generated client (`fetchClusterHighlight`, and `AuthImage` for the preview and the water crop, `frontend/src/api/admin/wvImportCvMatch.ts`) — that costs nothing, since their five minutes end before the token's fifteen do, and no token sits in their URLs, where it would outlast a refresh and land in access logs. For the fourth it does: `image-proxy` is a `fetch` carrying the header (`ImageOverlayDialog.tsx`, `useImageColorPicker.ts`), so `Vary: Authorization` now keys its `public` entry per token — an entry a shared cache was permitted to store and reuse across callers, `public` being RFC 9111 § 3.5's own exception. That keying costs more than it buys, the way it does on the geometry reads below: the picture depends on `?url=` alone and is identical for every caller, so what a shared cache would have handed on is a public Commons image, while the browser's own entry now expires with the token rather than after a day — an admin working through an import review re-proxies the same picture every 15 minutes, and each miss is another request to Wikimedia, whose politeness rules this repo otherwise keeps. It stays for the same reason the geometry reads keep theirs: a handler subtracting from a header another module set is a mechanism to introduce deliberately rather than in passing. The three SSE streams keep `private, no-cache` the same way, by their routes' declared `revalidate` policy (ADR-0071), and the `private` there is doing the work § 3.5 does elsewhere: `EventSource` cannot send headers, so their token rides in the query string and the request carries no `Authorization` at all — which is also why replacing the middleware's value rather than adding to it has to keep `private` deliberately. So do the division geometry read (`GET /api/divisions/:divisionId/geometry`) and the geoshape proxy (`GET /api/admin/wv-import/geoshape/:wikidataId`, Wikimedia's boundary for a Wikidata id, re-requested on every preview open), both by their routes' declared `revalidate` policy (ADR-0071) — and for the reason that decides the whole rule: every `/api/divisions` route is declared `admin` because the editor is its only caller, not because the answer is anyone's own — what it returns is GADM's boundary, at full resolution by default (2.8 MB of GeoJSON for France; the previews ask for a stored simplification, #1010), fetched again on every dialog open with no client cache in front of it. `no-store` there would trade a `304` for megabytes and protect nothing, and the same holds for the geoshape, whose body is Wikimedia's rather than anyone's own. Those reads keep the `Vary: Authorization` too, so they are bounded the way the `optionalAuth` ones are — the `304` within one token's lifetime, the full body on the first open after each refresh; a body identical to every caller gains nothing from that key, but a handler subtracting from a header another module set is a mechanism to introduce deliberately rather than in passing. One class sits ahead of the middleware, where it reaches four of five: the responses that hand the caller an access token — `/login`, `/verify-email`, `/refresh` and `/exchange-code`, plus `/change-password`, which is behind `requireAuth` and already carries the value — whose routes declare the `token` cache policy (`backend/src/api/route.ts`, ADR-0071), required at startup of any route whose response schema declares `accessToken`, so the five read alike. All five are `POST`, which no browser stores, but RFC 6749 § 5.1 asks a token response for the header outright, so they state `private, no-store` — and the `Pragma: no-cache` that RFC asks for beside it, deprecated in a response by RFC 9111 § 5.4 and read by nothing here, so it states the intent for an auditor rather than changing behaviour — rather than inherit the guarantee from the method. ### When each of these runs

Since #783 a gate runs when, and only when, the inputs it checks have changed,
and the scanners above sit on both sides of that rule. **gitleaks, Semgrep (both
scans), Trivy, `npm audit`, `pip-audit` and Bandit are gates in the map**
(`docs/tech/gates.md`, [ADR-0062](../decisions/0062-a-gate-runs-only-when-its-inputs-changed.md)):
the Node scan is pointed at the whole checkout and runs when any product path
moved — `backend/`, `frontend/`, `packages/`, `db/`, `martin/`, `scripts/`,
either compose file or `.env.example` — or any `cv-python/` path did, since its rule packs
carry Python rules; the Python scan and the image scan run when `cv-python/`
did, and `npm audit` when a manifest or lockfile did. gitleaks runs on a change
to any input class, since a secret can be pasted into any file. A backend
change cannot alter what the Python scan finds, and a prose change cannot alter
any of the others.
Time is the one input the map cannot name: Trivy, `npm audit` and `pip-audit`
answer from vulnerability databases, so a weekly `schedule:` run of the workflow
re-asks every gate whether or not a file moved. **GitHub's native secret scanning, push protection, the DCO
check and CodeQL's default-setup analyses are outside the map** and read every
change, whatever it touches: they are server-side or repository-wide, push
protection stops a provider's key at the push itself, and nothing in this
repository can skip them. Every skip the map does make is printed with the input class that
did not move, locally and in the CI run summary alike, so "that scan did not
run" is a checkable sentence rather than an absence.

## Semgrep Ruleset Composition

Both scans run `p/default` — Semgrep's own curated baseline — alongside the
targeted packs. It was added in #481, after a planted `eval(userInput)` produced
zero findings under the previous four-pack Node configuration. `p/default` flags
it as `javascript.browser.security.eval-detected`, and the probe is re-run
whenever this configuration changes: plant the call in a `.ts` and a `.js` file,
`git add -N` them (Semgrep only scans git-tracked paths), and confirm
`npm run security:scan` reports both and exits non-zero.

The other packs are kept rather than folded in, and that is a measurement rather
than an assumption. The measurement has to be **leave-one-out** — for each pack,
what is lost if it alone is removed from the configuration — and not pairwise
against `p/default`. Pairwise is the tempting version and it gives the wrong
answer: `react-unsanitized-property` is absent from `p/default`, which makes
`p/react` look load-bearing until you notice `p/owasp-top-ten` carries it too.

Rule ids at the pinned version, via `semgrep show dump-config p/<pack>`:

| Pack | Rule ids | Unique to it in the Node config | Unique in the Python config |
|---|---|---|---|
| `p/default` | 947 | **479** | **478** |
| `p/owasp-top-ten` | 503 | **67** | **38** |
| `p/secrets` | 50 | **1** — `detected-google-gcm-service-account` | **1** — same |
| `p/nodejs` | 36 | **0** | not in this config |
| `p/react` | 4 | **0** | not in this config |
| `p/python` | 139 | not in this config | **0** |

(Rule *ids* in a pack, not rules *run*: the run counts of 511 and 330 are what
survives filtering to the languages and files actually present.)

So three packs carry the configuration — `p/default`, `p/owasp-top-ten` and, by
exactly one rule, `p/secrets`. The language packs `p/nodejs`, `p/react` and
`p/python` contribute **nothing** at this version; each is fully covered by the
union of the others. They are kept anyway, and uniformly: dropping them would
trade a redundancy anyone can see for a silent dependency on Semgrep never
recomposing its packs, and the failure mode of that dependency is a rule
quietly ceasing to run. Rules are deduplicated by id, so the redundancy costs no
scan time. Re-run the leave-one-out when the pinned version is bumped — if a
language pack ever grows a unique rule again, that is worth knowing.

| `detect-non-literal-regexp` | 2 | One re-compiles an existing `RegExp` from its own `source` to add the `g` flag; the other is an alternation of regex-escaped literals — no quantifier over a group, so no catastrophic backtracking |
| `formatted-sql-query` + `sqlalchemy-execute-raw-query` | in `db/init-db.py`, `db/gadm_sample.py` and `db/tests/test_gadm_sample.py` | Each uses `sqlite3`, not SQLAlchemy, and interpolates two things only. One is a SQL **identifier**, which cannot be bound as a parameter, so it is validated instead: the GeoPackage layer name must match `TABLE_NAME_RE` where it is read out of `sqlite_master`, or the script exits. The other is `sql_filter`'s constant `WHERE "CONTINENT" = ?` clause, whose value is bound (#610). The suppressions ride on that check and that binding |

The one remaining fix was `missing-integrity` on `frontend/index.html`, which
loaded `maplibre-gl.css` from `unpkg.com` with no subresource integrity. Rather
than add an SRI hash, the tag was removed: `maplibre-gl` is already a frontend
dependency, so the stylesheet now comes from the package via `main.tsx`. That
drops a third-party runtime dependency and closes the gap where the hard-pinned
CDN version could drift from the one in `package.json`.

The web fonts went the same way (#653): Syne, Figtree and JetBrains Mono were
loaded from Google Fonts, so every page view sent the visitor's IP address to
Google (LG München I, 3 O 17493/20, found a site liable for exactly that). They
are served from the page's own origin now (`frontend/public/fonts/`, with their
OFL texts), so the shell — the page, its scripts, stylesheets and fonts —
contacts no third-party origin. What a page draws still can: the visitor's map
fetches its basemap tiles from `tile.openstreetmap.org` and its label glyphs from
`fonts.openmaptiles.org` (`MAP_STYLE`, `frontend/src/constants/mapStyles.ts`),
the admin's and editor's preview maps their basemap from
`basemaps.cartocdn.com`, and the pictures come from Wikimedia Commons
(ADR-0043).

## cv-python Hardening (V5/V8/V13/V16)

The Python service has a smaller surface than the Node backend but introduces new V5 (file upload) territory and a V8 boundary (intra-cluster traffic):

| Concern | Status | Notes |
|---|---|---|
| File upload size cap | enforced | `BodySizeLimitMiddleware` (`cv-python/app/middleware.py`) rejects requests with `Content-Length` exceeding `CV_MAX_BODY_BYTES` (default 100 MB; set in `.env`, which `docker-compose.yml` passes into the container, #1649) before the body is buffered, returning 413. Uvicorn has no equivalent CLI flag — middleware is the standard ASGI mechanism. |
| File-format validation | enforced | `decode_image()` checks `cv2.imdecode` return for `None` and rejects non-image bytes; image dimensions clamped after decode |
| Authentication | n/a (network-isolated) | Trust boundary documented above |
| Authorization | n/a | Service has no per-resource state |
| Error response sanitization | enforced | NDJSON `{"type":"error","message":...}` carries a generic message; full traces stay in container stdout |
| Worker-thread bounds | enforced | uvicorn `--limit-concurrency`; no unbounded `threading.Thread` daemons |
| Logging | implemented | Stdlib `logging` through `app/logging_config.py`, to stdout, collected by Docker. Level from `CV_LOG_LEVEL` (default INFO), timestamp, level and module on every line. A caught error is logged with its trace and answered with a generic message (`middleware.py`, `routes/pipeline.py`, #623) |
| Container | enforced | Non-root user, slim base, no secrets baked in, Trivy fails on **fixable** HIGH/CRITICAL (see the scanning row above for why unfixable ones do not block) |

## Known Gaps

- **Semgrep reads source files only.** `.semgrepignore` excludes `*.yaml`,
  `*.yml`, `*.json`, `*.sql` and `*.md`, so `p/secrets` never reads
  `docker-compose.yml`, `martin/config.yaml`, the workflows or any
  `package.json`. That no longer leaves them unwatched: gitleaks reads every
  tracked file (ADR-0108), and `p/secrets` matched provider formats only even
  where it does read (#596). What remains is a path no input class covers —
  the few files `docs/tech/gates.md` § Read by no gate lists and a tool's own
  settings file: a change to one of them alone does not run the scan, though
  the next change that runs it reads them.
- **Four files are only partially analysed by Semgrep.** Its parser reports a
  syntax error and analyses what it can: `martin/warm-tiles.sh`,
  `backend/src/services/wikivoyageExtract/parser.ts`,
  `frontend/src/components/WorldViewEditor.tsx`,
  `scripts/setup-integrations.sh` (the scan's own output names the line it
  stopped at on each run). The code itself is valid — `tsc` and
  ESLint pass on the two TypeScript files, and shellcheck on the two shell
  ones — so this is a limitation of Semgrep's own grammars, not a defect to fix
  in the source. Overall coverage
  is ~99.9% of lines. Running with `--strict` would turn this into a build
  failure, which is why the scans do not use it: it would fail every PR for a
  reason unrelated to security, and the alternative — excluding the files —
  would trade a warning for a real hole. Re-check when the pinned Semgrep
  version is bumped; parser coverage is the kind of thing that improves.
- **Semgrep's ruleset was narrower than assumed (resolved).** Until #481 the
  Node scan ran four targeted packs and not `p/default`, so a planted
  `eval(userInput)` produced zero findings in either `.ts` or `.js`.
  `p/default` is now in both scans — Node 266 → **511** rules, Python 199 →
  **330** — the 54 findings it raised were triaged (17 fixed, 37 suppressed
  inline with stated reasons), and the eval probe is confirmed to report and to
  exit non-zero. See [Semgrep Ruleset Composition](#semgrep-ruleset-composition).
- **CI ran no Semgrep until August 2026 (resolved).** The Security Scan job
  used the deprecated `semgrep/semgrep-action@v1`, pinned to semgrep 1.36.0,
  which died on registry rules carrying `severity: MEDIUM` and exited zero
  anyway — so the required check passed without scanning, in every run whose
  logs are still retained. Fixed by running the same npm scripts CI-side
  (#479).

  Scoped deliberately: this was a Semgrep outage, **not** a SAST outage. CodeQL
  (JS+Python, default setup) ran throughout — see the stack table above and
  `audit-2026-05-10.md` — so semantic and dataflow analysis was never absent.
  What went missing in CI was Semgrep's pattern layer, `p/secrets` included.
  Local `npm run security:*` was unaffected and did scan, so code that went
  through the documented pre-push tier was covered; the exposure was anything
  merged on CI-green alone. Recorded because "the check was green" is not
  evidence for that period.
- **World view visibility does not reach the tile server.** A declared route's `scope` and
  `getWorldViews` bound the REST API (see the security stack table above). Martin no longer
  auto-publishes tables — `martin/config.yaml` carries `auto_publish: { tables: false }`, which
  removed 27 table sources including every column of `experiences` — but `functions: true` still
  auto-discovers and publishes every compatible **function** in the database on its own public
  port (`ports:` in `docker-compose.yml`) with no authentication, so a hidden world view's
  geometry stays fetchable by tile id regardless of `is_public`. Five of the six published sources
  now take an id and answer a request that names none with an empty tile, and one that names a
  value that is not an id the same way, never a 500 with the database's error text (#664); the sixth,
  `tile_root_divisions`, takes none by design and draws the root GADM divisions for every
  caller alike. But the five do not all take the *world view's* id, so what a caller has to know
  differs by source. The three that answer for one world view take its id: `tile_region_islands`
  since #660 (the one the map itself drew unscoped), `tile_world_view_root_regions` and
  `tile_world_view_all_leaf_regions` since #662; until then both filtered on
  `p_world_view_id IS NULL OR …`, so a request naming no world view answered for all of them at
  once and a hidden world view's regions came back without anyone having to guess anything.
  `tile_region_subregions` reads the same table and takes a **region** id instead, with no
  world-view filter at all, so a hidden world view's subtree is reachable from any region id
  inside it without its own id ever being known. And the **default** world view is behind no id
  whatsoever: its map is GADM itself, drawn by `tile_root_divisions`, which takes no
  parameter, and `tile_division_subdivisions`, which takes a division id — so a default world view
  whose `is_public` is false is served unauthenticated with nothing to know. `is_public` governs
  it exactly as it governs any other world view and `is_default` carries no visibility meaning of
  its own, which is what makes that a reachable state rather than a hypothetical one
  (`docs/tech/world-views.md` § The default World View). Requiring the parameter narrows this
  gap; the ids are small integers, and of the six sources
  only three answer for a named world view at all — two take a different id and one takes none —
  so it does not close it. That set is discovered, not
  enumerated: it currently resolves to the six `tile_*` functions in `martin/README.md` § Function
  Sources, and a newly added compatible function would be published the same way, with no edit to
  `martin/config.yaml`. A Martin-level `postgres.functions` allowlist could pin those six
  explicitly, but building one now would be work the fix below throws away: once Martin sits
  behind an authorizing proxy, the proxy decides access per request and a function-name allowlist
  is redundant. The fix is the pattern already used for cv-python below: drop the `ports:` mapping
  so Martin is reachable only on the Docker compose network (`expose:` only), plus an authorizing
  proxy in the backend (e.g.
  `/api/tiles/:source/:z/:x/:y` against a per-source allowlist) that MapLibre reaches via
  `transformRequest`. Deferred to the tile-boundary follow-up branch, which will carry its own ADR.

  The `auto_publish: { tables: false }` change above is not live merely because it is committed.
  `docker-compose.yml` bind-mounts `martin/config.yaml` read-only and starts Martin with
  `--config /config.yaml`, so a running container keeps its old catalog — the 27 retired table
  sources keep being served — until it is recycled. On a deployed instance, restart Martin and
  confirm with the same two checks used to verify this fix:

  ```bash
  docker compose restart martin
  curl -s localhost:3000/catalog | jq '.tiles | keys'      # function sources only
  curl -s -o /dev/null -w '%{http_code}\n' localhost:3000/experiences.1/14/8186/5447   # 404
  ```

  The scope requirement above has the same property for the same reason, one layer down. A
  function definition lives in the database, not in the image, so it reaches an existing instance
  only when `db/init/01-schema.sql` is re-applied there (the signatures do not change, so
  `CREATE OR REPLACE` carries it and no migration file is involved). And a running Martin holds an
  in-process tile cache — `cache_size_mb` is unset in `martin/config.yaml`, so its default is in
  effect — which is keyed on the request URL: measured on the development stack, an unscoped tile
  already served kept answering `HTTP 200` with the old bytes after the functions were replaced,
  while an unscoped tile not yet in the cache answered `HTTP 204`. Restart Martin after applying,
  and verify on a tile the cache cannot already hold:

  ```bash
  curl -s -o /dev/null -w '%{http_code}\n' \
    'localhost:3000/tile_world_view_all_leaf_regions/5/16/11'                   # 204
  curl -s -o /dev/null -w '%{http_code}\n' \
    'localhost:3000/tile_world_view_all_leaf_regions/5/16/11?world_view_id=5'   # 200
  ```

  The first line holds anywhere; the second names the development database's world view, and needs
  substituting for an id whose world view actually has regions inside the tile chosen — the same
  caveat `docs/tech/performance.md` carries for the probe's defaults. Two `204`s otherwise read as
  a deploy that did not land, when what they are is an empty tile for a scope with nothing in it.
- cv-python logs through stdlib `logging` to stdout (#623), with no structured (JSON) format and no correlation id per upload, so two curator jobs' lines interleave without a key to tell them apart. Acceptable at L2, since the service has no auth/authz events to log. A request id is the next step once the audit and observability story expands.
- Python dev tooling (`mypy`, `pytest`, `bandit`) lives in `cv-python/requirements-dev.txt` and requires a venv at `cv-python/.venv` for the local gates — not tools on PATH, which the npm scripts never reach: each one invokes `.venv/bin/<tool>` by path, and `scripts/require-py-tools.sh` now fails the gate outright when they are absent rather than letting it read as environment noise. CI covers both shapes across two jobs: the checks job builds the same venv with `npm run setup:py:dev`, and the Python test job installs into the runner's own interpreter with `actions/setup-python` + pip.
- **Overridden transitive dependency (September 2026):** `qs` — [GHSA-x5fp-wj9c-mxmx](https://github.com/advisories/GHSA-x5fp-wj9c-mxmx) (array-limit bypass via bracket-key comma parsing) and [GHSA-4mjr-xmp4-gh2g](https://github.com/advisories/GHSA-4mjr-xmp4-gh2g) (denial of service via an attacker-controlled `isBuffer`), both moderate, fixed in `qs 6.16.0`. `qs` is not a direct dependency: `express 4.22.2` → `body-parser 1.20.6` resolves `qs 6.15.x`, and no express-4 release with a patched body-parser existed on the day the advisories were published, so `npm audit` failed on every branch. `backend/package.json` carries `"overrides": { "qs": "^6.16.0" }` — a minor of the same major, the version the advisories name as fixed — which the lockfile applies under express and body-parser. **Remove the override once express 4 ships a body-parser that resolves `qs >= 6.16` on its own (or on the express 5 migration);** the audit gate says nothing when the override becomes redundant, so check `npm ls qs` in `backend/` when express or body-parser is bumped.
