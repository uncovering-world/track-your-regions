# Gates

A gate runs when, and only when, the inputs it checks have changed. `scripts/gates.mjs` is the map
from each gate to the files it reads, and the only place that map is written; `npm run gates` prints
what the change in the working tree asks for, gate by gate, with the reason each skipped one was
skipped. A change set the runner cannot work out — a shallow clone, an unknown base — runs
everything and says so, and a path that is an input to nothing is reported rather than dropped. The
two tables below are generated by `node scripts/gates.mjs --table` and pinned to it by
`scripts/gates.test.mjs`, so they cannot drift from the map they describe (#783).

## Reading a run

```bash
npm run gates                      # what the working tree asks for, against main
npm run gates -- --base origin/main --rev my-branch
npm run gates -- --json            # the same decision, as data
TEST_REPORT_LOCAL=1 npm run gates -- run test --affected  # the unit lanes, only the specs the change reaches
node scripts/gates.mjs --table     # regenerate the two tables below
```

A run opens with the range it measured and the input classes that range touches,
and then answers for every gate in the map. The docs-only commit 82b0345d, which
edited one file:

```text
$ node scripts/gates.mjs --base 82b0345d^ --rev 82b0345d
Change against 82b0345d^ (merge-base 3e6ac38): 1 paths
Inputs touched: docs

check lint:backend          skipped  inputs untouched: backend, shared
check lint:frontend         skipped  inputs untouched: web, shared
…
check security:secrets      runs     inputs touched: docs, prose
…
check lint:md               runs     inputs touched: docs
check lint:links            runs     inputs touched: docs
check lint:pointers         runs     inputs touched: prose
check lint:shrunk           runs     inputs touched: docs, prose
…
stack test:e2e:smoke        skipped  inputs untouched: backend, web, shared, database, tiles, runners, compose
stack perf                  skipped  inputs untouched: backend, web, shared, database, tiles, runners, compose
```

`security:secrets`, `lint:md`, `lint:links`, `lint:pointers` and `lint:shrunk` run, and every other one
names the input class it did not see move. Three shapes of answer are worth recognising:

- **`inputs touched: <class>`** — the gate runs, and the class says which of its
  inputs moved.
- **`every gate applies`**, under a line naming the reason — the root
  `package.json` changed outside its scripts and dependencies, a run in CI saw
  the map or the workflow change (§ What a tool's settings ask for), or the
  change set could not be worked out (no base, a shallow clone, a git that would
  not answer). The reason is printed
  once above the list rather than repeated on every line of it.
- **`Not an input to any gate: …`**, at the end — paths that belong to no class.
  They are reported rather than dropped: a file nothing reads is a fact about the
  map, not about the change.

Against `HEAD` the comparison includes the working tree and the files git does
not track yet, so `npm run check` answers for what is on disk rather than for
what is committed.

With no `--base` and no `GATES_BASE`, a local run measures against `main`, or
against `origin/main` when that has moved past it (`freshestBase`). A clone's own
`main` falls behind every merge made on GitHub, and a branch measured against a
stale one counts every file merged since as its own, asking for gates nothing on
the branch touched. A local `main` with commits of its own is kept.

The change set is listed from the merge base, which keeps out what the base's
own line gained since the fork. The one exception is a `--base` that is no
ancestor of the revision and does not lie on `main`'s line either (`listFrom`):
a pushed head the branch has been rewritten past, by a review wave folded into
its commits or by a rebase. Its merge base is the fork from `main`, which would
read the wave as the whole branch, so the two trees are compared instead, and
the change line says so. After a rebase onto a newer `main` that also lists what
`main` moved, which over-reports rather than misses. A `main` that moved on
since the fork (`--base origin/main` after a merge on GitHub) keeps the merge
base, and `GATES_BASE` always takes it, since CI sets it from the event,
never from a head the branch was rewritten past.

## The tiers

| Tier | What it holds | Owed locally | What runs it |
| --- | --- | --- | --- |
| `check` | the fast gates: lint, typecheck, knip, the circular-import pass, the generated row types against the schema, the docs pass, the line-pointer pass over every file that carries prose, the workflow lint, the fast security audits | before every commit | `npm run check` — `npm run check:all` forces every one |
| `test` | the unit lanes, Node and Python | before every commit, narrowed to the specs the change reaches | `TEST_REPORT_LOCAL=1 npm run gates -- run test --affected` (§ Running only the specs a change reaches) |
| `scan` | the slow scans: Semgrep on both stacks, the Trivy image scan | no: CI runs them | `npm run security:all` — the `check` tier, then this one |
| `stack` | build, smoke, the database lane, the API lane, Lighthouse: the lanes that stand a stack up | only a measurement marked `run here` | `npm run gates -- run stack` **lists** them as `run here`, `CI runs it` or `skip`, and exits 2; they are typed by hand |

**Where each tier runs (#1379).** The local loop is for fast feedback, and CI is
where the slow lanes run: it runs every lane a change asks for on every pushed
head. A local run of a lane CI also runs therefore repeats it on a slower
machine and finds nothing CI would not. So:

- **Before every commit:** the `check` tier and the selected unit lanes. A
  review wave measures both against the pull request's pushed head
  (`--base <head>`), which CI has already answered for, so its own edits are
  all it runs.
- **By hand:** a measurement a stack lane lists in `local`, when the change
  touches a class it names. `perf` lists two, each under its own command:
  `perf:local`, Lighthouse on the dev stack's real catalogue where CI's lane
  weighs a fixture, on a change to what the browser loads (`web`, `shared`);
  and `perf:api`, the latency probe over the hot reads and tiles, which no CI
  job runs, on a change to what answers them (`backend`, `database`, `tiles`,
  `shared`). A change to a measurement's own runner (`scripts/perf-local.sh`,
  `scripts/perf-api.mjs`), which no CI job runs, owes it too. `perf:local`
  runs the probe as its last step, so the two are never owed side by side.
  Both measure the dev stack, which serves the main checkout, so they are run
  where the branch is what that checkout holds.
- **On a red CI lane:** that lane alone, reproduced locally.
- **Before merging:** every check that ran on the head is green. The slow
  lanes are not among the contexts branch protection requires, so this is the
  rule that makes them count. One check is exempt, and only on one kind of
  pull request: on a PR that changes `.github/workflows/claude-review.yml`,
  the `review` check fails by design with "reported success without running"
  — the review action refuses a workflow that differs from `main`'s copy — and
  the summary a `/review` comment brings answers for it instead (#483). Any
  other failure of that check on such a PR counts as a red check.

```text
$ npm run gates -- run stack
The stack tier, lane by lane — CI runs every lane this change asks for on every pushed head:

  CI runs it build            npm run build && npm --prefix frontend run size  (inputs touched: web)
  CI runs it test:e2e:smoke   npm run test:e2e:smoke  (inputs touched: web)
  skip       test:db          npm run test:db  (inputs untouched: backend, shared, database, runners, compose)
  skip       test:api         npm run test:api  (inputs untouched: backend, shared, database, runners, compose)
  run here   perf             npm run perf:local  (inputs touched: web; Lighthouse on the dev stack's real catalogue, where CI's lane weighs a fixture: a change to what the browser loads)
```

A `run` stops at the first failure, then prints what it did, what broke, what
never got its turn and what this change never asked for. The `check` tier over a
cv-python-only range, on a host with no `python3.12`:

```text
$ node scripts/gates.mjs run check --base 9f3351c0^ --rev 9f3351c0
▶ check:py  npm run check:py
Python dev tooling is missing: ruff mypy

These gates did NOT run. This is a failure, not a skip.
[the guard's container command follows]

Ran: check:py
Failed: check:py (exit 1)
Not run (stopped after check:py failed): security:py:bandit, security:py:deps
Skipped (inputs untouched):
  lint:backend         inputs untouched: backend, shared
  …
  lint:links           inputs untouched: docs
```

The distinction in the guard's own words is the one to carry: a gate the **map**
skips had nothing to read, and a gate the **host** cannot run is a failure to
report. They are printed differently because they mean different things.

A gate whose image the **registry** refuses is the third case (#1316). Before a
Docker gate runs, the runner pulls every image it pins by digest — in its npm
scripts or in a runner file they run, as `api:breaking` keeps oasdiff in
`scripts/openapi-breaking.mjs` — and that pin stays the one statement of the
image's version (`imagesOf`); an image already on the host is not pulled
again. A pull refused for a reason that is the environment's — Docker Hub's
anonymous limit (`toomanyrequests`), a timeout, a refused or reset connection,
a name that does not resolve (`REGISTRY_REFUSAL`) — stops the tier before the
gate runs, with the registry's own line and exit 75 (`ENVIRONMENT_FAILED`,
EX_TEMPFAIL):

```text
▶ lint:openapi  npm run lint:openapi
lint:openapi could not run: the registry refused redocly/cli:…@sha256:… (toomanyrequests: You have reached your unauthenticated pull rate limit). That is the environment's failure, not the gate's verdict on the change: run it again once the registry answers.
Failed: lint:openapi (the environment: the registry refused an image it runs; exit 75)
```

A pin that names no manifest is not among those reasons: that is the
repository's error, and the gate runs and fails on it as itself.

A tier whose gates all sit on untouched inputs prints the sentence rather than
nothing at all — on a clean `main`, `npm run check` says

```text
Nothing to run for tier check: no changed path is an input to lint:backend, lint:frontend, typecheck:backend, typecheck:frontend, knip:backend, knip:frontend, lint:shared, typecheck:shared, knip:shared, lint:circular, db:types, security:deps, security:secrets, lint:shell, lint:docker, lint:actions, lint:md, lint:links, lint:openapi, api:breaking, api:client, lint:pointers, lint:shrunk, check:py, security:py:bandit, security:py:deps. `--all` runs every gate.
```

and exits 0. That is the one line this runner exists to print: a gate that did
not run has to say so, because silence and success look identical in a log.

The opposite case says as much. Where every gate applies — a change set the
runner could not work out, or a change only every gate can answer for —
the run opens with the sentence that made it so before the first gate starts:

```text
$ GATES_BASE= node scripts/gates.mjs run stack
GATES_BASE is empty: nothing to diff against, so every gate applies.
```

Without it a reader sees every gate in the map run, or a stack listing whose every line
reads `(every gate applies)`, and has to guess whether the branch really touched
everything or the base was simply unknown.

## Reusing a pass

A gate that passed on the same inputs is not run again (ADR-0091). Folding
review fixes into the commits they belong to, a rebase that applies cleanly and
a review wave of Markdown alone all leave the files a lane reads exactly as
they were. Before this, each of them cost the lane's whole run again: a median
of 278 s for `test:frontend` on the development machine.

`run` hashes, for each gate, every file in its input classes as it sits on disk,
and whether git tracks it. `lint:shell`, `lint:docker` and `lint:pointers` read
only what git tracks, so staging a new file moves their key. The hash also covers:

- the files in the gate's own `config` (§ What a tool's settings ask for);
- the gate machinery and the root manifests: `scripts/gates.mjs`,
  `scripts/gate-cache.mjs`, `package.json` and `package-lock.json`, so a pass
  recorded under older machinery is never reused;
- the Node manifests and lockfiles of the three packages;
- the command;
- the Node version, and the Python version for a Python gate;
- for a unit lane, whether it runs on the host (`TEST_REPORT_LOCAL=1`) or in the
  backend container, since the container has no git and mounts only part of the
  tree.

That hash is the gate's key. `scripts/gate-cache.mjs` holds the key and the
records. If a pass is recorded under the key, the gate is not spawned. The run
prints it on a line of its own and names it again in the summary:

```text
✓ test:frontend  reused: passed on these inputs at 2026-10-11T15:00:00.000Z (abc1234)
▶ test:backend  node scripts/test-report.mjs backend-unit
…
Ran: test:backend
Reused (passed on the same inputs, not run again): test:frontend (2026-10-11T15:00:00.000Z, abc1234)
```

What is and is not recorded:

- **Only a pass is recorded.** A failure, a gate the host could not run, and a
  gate killed by a signal leave nothing behind.
- **A pass whose files moved while it ran is not recorded.** The run hashes the
  files again after the gate exits, and records the pass only if both hashes
  agree. Otherwise the summary names the gate under `Not recorded (files changed
  while the gate ran)`.
- **A gate whose answer reads something outside the tree is never reused.** The
  dependency audits read advisory databases, Semgrep fetches its rule packs, Trivy
  reads a vulnerability database, `api:breaking` reads the base's document, and
  `lint:links` resolves links to files of every type while its class holds the
  Markdown only.
  The *Pass reused* column of the gates table below names each of them with its
  reason, from `uncached` on the gate's entry in the map.
- **The stack tier is listed, never run,** so nothing records its passes.

Records sit under the clone's common git directory, `<git-common-dir>/tyr-gates/`,
so the worktrees of one clone share them and nothing is tracked. Deleting that
directory forgets every pass.

Three things run every gate the change asks for:

- **`--no-cache`** on `run` (`npm run gates -- run test --no-cache`);
- **`--all`**, which forces every gate of the tier, so `npm run check:all` reuses
  nothing either;
- **CI**, which never reads or writes a record. A run with `CI` set reuses
  nothing: a fresh checkout is what answers for a pushed head.

## Running only the specs a change reaches

`npm run gates -- run test --affected`, on the host (`TEST_REPORT_LOCAL=1`), runs
of each Node unit lane only the specs the change reaches (#1376). Measured on the
development machine on 2026-10-11, a change to
`backend/src/services/sync/componentItemMatching.ts` reached 57 of the backend
lane's 287 spec files, which ran in 29 s against the lane's median of 80 s.
`scripts/affected-specs.mjs` makes the selection, and Vitest follows the import
graph (`vitest related`) from:

- **the changed modules** of the lane's trees: `backend/src`, `scripts/` and
  `packages/shared/src` for the backend lane; `frontend/src`, `frontend/perf`,
  `frontend/tests`, `packages/shared/src` and `scripts/` for the web's;
- **every spec that reads files as text**, which no import graph can follow:
  `repoFile()`, `readFileSync`, a directory walk, an ESLint run over the source.
  They run whenever the lane runs. That
  is how a change to `frontend/src/components/regionMap/useMapInteractions.ts`,
  which no backend spec imports, still runs `db/regionFocusAntimeridian.test.ts`,
  which reads it;
- **the module loaders**, which import other modules by a computed path:
  `api/responseModules.ts` lists `api/responses/` and imports each file, so a new
  response module reaches `responseModules.test.ts` through no import. A loader
  is found by its `await import(<expression>)`, and its importers run whenever
  the lane does.

A file a module reads at run time rather than imports is something no graph
follows either: `loadPricing()` opens `backend/src/data/openai_api_model_costs.csv`,
and `pricingService.test.ts` imports the module, not the file. So a changed file
under a lane's trees that the graph does not follow — anything but code and what
a bundler imports beside it — runs the whole lane.

What is left is followed: a changed module through the graph, a file a spec reads
through that spec. So a change whose selection is empty reaches no spec, and the
lane is not started: an edit to `frontend/index.html` alone, which no Vitest spec
imports or reads, starts nothing. A change to a module of the lane's trees that
no spec imports starts the lane with that module, and Vitest finds no spec for it.

The lane runs whole instead, and says why, when the selection cannot answer for
the change:

- the lane's configuration changed: its Vitest config, the web's setup file, a
  manifest or lockfile, a TypeScript config, or `scripts/test-report.mjs`, the
  runner the lane goes through;
- a module of its trees was deleted or moved, whose importers the graph can no
  longer find;
- a file under its trees that the graph does not follow changed: data a module
  may read at run time;
- a compose file changed, which shapes the lane's container and is read by no
  module;
- the change set is unknown.

Each lane prints its selection before it runs and the count after, and a
selection that reaches nothing says so instead of passing in silence:

```text
▶ test:backend  node scripts/test-report.mjs backend-unit
  affected specs: 8 changed modules of the lane's trees, and 30 specs that read files as text, which a change to the files they read asks for; 287 spec files in the lane
…
Backend Unit/Integration: ran 33 of 287 spec files, the affected selection.
```

```text
○ test:frontend  affected specs: 0 changed modules of the lane's trees, and 0 specs that read files as text; no spec of the lane reaches the change
…
Not started (the change reaches no spec of the lane): test:frontend
```

```text
Frontend Unit/Integration: ran 0 of 188 spec files, the affected selection.
Frontend Unit/Integration: no spec of the lane reaches the change.
```

The selection reaches the lane through two variables, `TEST_REPORT_RELATED` (the
paths for `vitest related`) and `TEST_REPORT_SPEC_TOTAL`. A run that is not
selected clears them, so a value inherited from a shell never narrows a whole
lane. Three more limits:

- **A selected run is never recorded as the lane's pass** (§ Reusing a pass),
  since it ran only some of the specs. A whole pass already recorded answers for
  it.
- **The container shape runs the whole lane** and says so.
- **CI never selects.** It runs every lane whole on every pushed head.

## The web unit lane

What a whole run of the web lane costs is mostly not its tests. Vitest's own
breakdown of one run splits the time it spent across the workers into
transformation, setup, imports, the DOM environment and the tests themselves,
and on 2026-10-11, on the development machine (4 cores), the imports alone came
to more than the tests and the environment together. The icon package's index,
`@mui/icons-material`, was most of that: it loads every one of its icons, and
each spec file whose graph reached one of the 37 imports from it loaded them
again. Requiring the index takes 3–4 s in Node, one icon 0.25 s.

Three changes were adopted, each measured as one full run, `vitest run` in
`frontend/` under the shared lock, 188 spec files and 1985 tests, all green. The
first two (#1377) at the load the machine usually carries:

| Run | Wall | Transform | Import | Environment | Tests |
|---|---|---|---|---|---|
| Before | 310 s | 85 s | 487 s | 160 s | 158 s |
| One path per icon | 238 s | 12 s | 242 s | 174 s | 180 s |
| One path per icon, `pool: 'threads'` | 222 s | 11 s | 219 s | 163 s | 179 s |

- **One path per icon.** Every icon is imported by its own path
  (`@mui/icons-material/Delete`), and the frontend lint refuses the package
  index (`no-restricted-imports` in `frontend/eslint.config.mjs`). The bundle
  tree-shook the index already, so the app's build does not change; the
  saving is the lane's.
- **Worker threads** (`pool` in `frontend/vite.config.ts`). Each spec file
  still gets a fresh module graph and environment; a thread costs less to
  start than a child process. No spec of the lane needs a process of its own.
- **happy-dom instead of jsdom** (`environment`, ADR-0093, #1388), which builds
  a document for less. Neither is a browser: both have no layout, WebGL or
  workers, and a spec that works around one of those says which. Measured with
  the machine idle at the start of the run (below):

| Run | Wall | Transform | Import | Environment | Tests |
|---|---|---|---|---|---|
| Both #1377 changes, jsdom | 207 s | 9 s | 203 s | 158 s | 157 s |
| Both #1377 changes, happy-dom | 186 s | 9 s | 205 s | 115 s | 133 s |

Two more were measured and not adopted:

- **`isolate: false`** (`--no-isolate`) breaks the specs rather than speeding
  them: modules mocked by one file leak into the next, and at least 27 spec
  files failed before the run was stopped, `ChunkBoundary.test.tsx` among them
  waiting out 170 s per test. Telling the files that hold no module state from
  the rest is a classification every new spec would have to keep up to date.
- **Vitest's dependency optimizer** (`deps.optimizer.client`) made the run
  slower, 329 s against 310 s, since it pre-bundles what the lane would have
  loaded anyway.

The #1377 figures were taken at the load the machine usually carries, a load
average near 4, which is also the load the lane has to pass at: the specs that
time out under load (#1239) passed in every run. The pair that matters was
taken again with the machine idle at the start of each run (a one-minute load
average below 1.5): 336 s before, 207 s with both changes, and 186 s under
happy-dom on 2026-10-12, every spec green. A whole run fills all four cores by
itself, so idle describes only what else the machine was doing.

## What a tool's settings ask for

No tool's settings ask for every gate (ADR-0092). Each
file a gate reads outside its classes is in that gate's `config`, the way a
target's own settings are its input in Nx, and asks for that gate alone:

- `.madgerc` asks for `lint:circular`, `.markdownlint-cli2.jsonc` for `lint:md`,
  `.semgrepignore` for the two Semgrep scans, `.gitleaks.toml` for the secrets
  scan;
- a tool guard (`scripts/require-node-tools.sh`, `scripts/require-py-tools.sh`,
  `scripts/require-python-312.sh`) asks for the gates whose script calls it,
  `scripts/scan-image.sh` for the image scan and `scripts/scan-secrets.sh` for
  the secrets scan;
- the root `package-lock.json` asks for the two gates that run a root tool,
  `lint:circular` and `lint:md`;
- `docs/tech/gates.md`, `ci.yml` and the root `package.json` ask for
  `test:backend`, whose specs read them.

The root `package.json` is read by script, the way Nx reads a root `tsconfig` by
path mapping. A change to one npm script asks for the gates that run it, or run
a script that runs it: an edit to `format:py` asks for `check:py`, which calls
it. The listing names it as `runs the changed npm script format:py`. A change
outside the scripts and the dependencies, to `engines` say, cannot be placed,
and asks for every gate.

**The map and the workflow are global in CI only.** A change to
`scripts/gates.mjs` or `.github/workflows/ci.yml` runs every gate in CI, and so
does a change to a root npm script the workflow runs by name (`npm run check`,
`npm run perf`, `npm run setup:py:dev`, read from the workflow by
`workflowScripts`), since that script is part of a job's definition. An edit
that narrows the map could otherwise skip the very gate it broke, and a job's
definition is tested only by running it. Locally the same change asks for
its readers alone: the map's and the workflow's specs in `test:backend`,
actionlint, the docs gates. The listing says so on a line of its own:

```text
.github/workflows/ci.yml decides what CI runs, so CI runs every gate for this change; locally its readers do (ADR-0092).
```

So a pull request that edits the map runs its own specs locally, and CI answers
for the rest before it merges.

With no class that runs everything, a file a gate reads but the map never names
would be checked by nothing, locally or in CI. Two specs in
`scripts/gates.test.mjs` hold the map complete:

- **Every tracked path is placed.** It is in a class, in a gate's `config`, or
  in the *Read by no gate* table below with its reason. A new file fails the
  spec until the map says who reads it.
- **Every file a gate's npm script names is that gate's input.** A guard or
  runner the script calls by path (`./scripts/require-py-tools.sh`), and any
  root `.…rc` file it names, is in the gate's classes or `config`, and in its
  cache key.

A tool's settings that its script does not name (`.madgerc`) can only be placed
by hand. The first spec is what makes sure the file is placed at all.

## The map

### Inputs

| Input | Paths | Why this is what it is |
| --- | --- | --- |
| `backend` | `/^backend\/(?!.*\.md$)/` | The API's source, its specs and its build. The web reads none of it: the backend's response schemas reach the web only as the OpenAPI document in packages/shared (ADR-0072, ADR-0073), which api/openApi.test.ts holds to the schemas. So a backend change that leaves the document as it was asks for the backend's own gates and the lanes that run the stack. |
| `web` | `/^frontend\/(?!.*\.md$)/` | The web client, its specs and its Playwright and Lighthouse runners. The backend unit lane reads frontend/src through repoFile() — the URL safety and antimeridian scans — so a change here still asks for test:backend; none of the backend's other gates reads it. |
| `shared` | `/^packages\/(?!.*\.md$)/` | The rules both sides import (ADR-0065) and the OpenAPI document the web's client is generated from (ADR-0072): both typechecks read it through the link, and its specs run in the backend unit lane. A change here asks for both sides. |
| `database` | `/^db\/(?!catalogue-coverage\/.*\.jsonl$)/` | The schema, the migrations and the loaders: what a database is built from. The backend unit lane reads db/ through repoFile() — schema parity, the migration ledger, the trigger guards — and the stack lanes stand on it. No lint, typecheck or web gate reads it. |
| `tiles` | `martin/` | Martin's configuration. The backend unit lane asserts on the tile sources it publishes, and the smoke and Lighthouse lanes draw them. |
| `scripts` | `scripts/` | The repository's own scripts and their specs, whole: the tooling specs run in the backend unit lane, and two of its specs scan the tree for anything that switches the geometry triggers off. |
| `runners` | `/^scripts\/(?!.*\.test\.mjs$)(?!(?:affected-specs\.mjs\|board\.sh\|catalogue-coverage\.sh\|check-shrunk-files\.mjs\|ci-graph-measure\.mjs\|db-cli\.sh\|db-migrate\.sh\|db-types\.sh\|gate-cache\.mjs\|gates\.mjs\|lib\/db-env\.sh\|lint-line-pointers\.mjs\|match-snapshot\.sh\|openapi-breaking\.mjs\|require-node-tools\.sh\|require-py-tools\.sh\|require-python-312\.sh\|review-surface\.mjs\|scan-image\.sh\|scan-secrets\.sh\|setup\.sh\|setup-integrations\.sh\|test-db-migrate\.sh)$)/` | The scripts the unit and stack lanes run through: test-report.mjs, test-stack.sh, the report parsers the web's specs import, the API contract and performance runners. ## What the backend suite reads across the repository

The product is one contract surface split across the classes `backend`, `web`,
`shared`, `database`, `tiles`, `scripts`, `runners` and `compose` (#1378). Each gate
reads the classes it opens, and only those. Before the split one class, `app`,
held all of them. A change of backend source therefore ran the web's lint,
typecheck, knip and unit lane (a median of 278 s on the development machine),
none of which can see a file under `backend/`.

The two sides meet in `packages/shared`, the `shared` class. Both sides import
it: the rules both apply, declared once (ADR-0065). A change to a shared rule is
a change to both sides, and both typechecks read its source through the link.
So a `shared` change asks for every gate of both sides.

The package also carries the OpenAPI document the web's client is generated
from (ADR-0072, ADR-0073). That document is the only path from the backend to the
web: a backend change that leaves it as it was cannot move a web type or a web
spec, which is why a `backend` change asks for no web gate. Three gates follow
from the document for an endpoint whose answer a schema declares:

- `backend/src/api/openApi.test.ts`, in the backend unit lane, fails while the
  document lags the schemas;
- `api:client` fails while the web's client lags the document;
- the frontend's typecheck sees a change to that answer.

A success body sent around `respond()`, and so declared by no schema, fails
`lint`: `RESPONSE_SHAPE_RULES` in `backend/eslint.config.mjs`. The endpoints it
exempts line by line have no caller on the web (#1006, #1033), so no web gate
reads their answers at all.

In the other direction the backend
suite reads the rest of the repository directly, through `repoFile()` in
`backend/src/testSupport/` (#948), and the tooling specs beside it under
`scripts/` do the same through `scripts/repo-root.mjs`. Everything the two
reached on 2026-10-03:

| What a spec opens | Why |
| --- | --- |
| `db/init/01-schema.sql`, `db/migrations/` (and named migrations under it) | the schema-parity and migration guards compare SQL as text |
| `db/catalogue-coverage/` | `services/catalogueCoverage/files.test.ts` reads the committed register, regions and lists whole and names every wrong line (ADR-0081). No other spec reads those files, so their `.jsonl` lines are a class of their own, `coverage`, which asks for this lane and the Node Semgrep scan, whose `p/secrets` pack reads them too: a pull request that changes a list runs no lint, build or stack lane |
| `frontend/src/components/regionMap/useMapInteractions.ts` | one rule, one runtime: the spec asserts that the map's own division paths frame from the stored box rather than measuring (#674). The client's *copies* of a rule the database also holds — the near-global threshold, the label fold, the action vocabulary — are gone: both sides import `packages/shared` (ADR-0065), and the schema is held to it by a type |
| `frontend/src` as a whole tree | `types/urlSafety.test.ts` and `db/regionFocusAntimeridian.test.ts` scan it for a second decision made anywhere in the client (#672, #674) |

That list is not maintained by hand. `scripts/gates.test.mjs` reads every
`repoFile()` call whose arguments are string literals — in the backend suite and
in the tooling specs beside it under `scripts/`, which `backend/vitest.config.ts`
runs in the same gate — resolves each to a repository path, and asserts it is in
one of `test:backend`'s classes or its `config`. The `docs/tech/gates.md` and
`.github/workflows/ci.yml` rows arrived that way:
`scripts/ci-failsafe.test.mjs` reads `.github/workflows/ci.yml`, and the
assertion is green only because `test:backend`'s `config` names that path. A
spec that starts reading a path the map does not name turns the test red, and
the reason it must is the failure the assertion names: a path in no input class
means a change to that file alone touches no input, so the unit lane is skipped,
reports Success, and the spec written to guard that very file never runs (#952).

## How CI applies the map

`.github/workflows/ci.yml` opens with a `Changes` job that checks out with
`fetch-depth: 0`, works out the base — the pull request's base sha, the push
event's `before`, or an all-zero sentinel for a manual dispatch — and runs
`node scripts/gates.mjs --github-output`. That writes one `job_*` key per job
plus a one-line `reason`, and a second step prints the full verdict into the log
and the run summary, because with `$GITHUB_OUTPUT` set the script writes nothing
to stdout and the decision would otherwise be invisible.

Every other job reads those outputs in its own `if:`:

```yaml
if: ${{ !cancelled() && (needs.changes.result != 'success' || needs.changes.outputs.job_check == 'true') }}
```

Three things about that line are load-bearing.

- **`!cancelled()` removes the implicit `success()`.** A `Changes` job that
  *fails* therefore skips nothing: every job runs, which is the map's own rule
  for an unknown change set applied one level up. Without it a broken decision
  would skip the required contexts — `Lint & Type Check`, `Security Scan`,
  `Unit Tests`, `E2E Smoke` and `Performance (Lighthouse)`, the last two
  required since #1099 made the API contract lane in `E2E Smoke` blocking —
  each would report Success, and the pull request would be mergeable with
  nothing run on it.
- **No job waits on another but `Changes`.** The build, the smoke lane and
  Lighthouse used to wait on `Lint & Type Check`. The waits came out when they
  were measured (§ The job graph).
- **The filter is on the jobs and never on `on:`.** A workflow skipped by a
  `paths:` filter never reports its checks, so the required ones would stay
  Pending and the merge button would never light up. A job skipped by its own `if:` reports Success and satisfies
  the same required check (ADR-0062 decision 2).

**Every job that pulls or builds through Docker Hub logs in first** (`Lint & Type Check`, `Security
Scan`, `Trivy Image Scan`, `E2E Smoke`, `Performance (Lighthouse)`; `docker/login-action`, pinned
by commit). Anonymous pulls count against a budget every GitHub-hosted runner behind one address
shares, and on 2026-10-09 a busy hour drew `toomanyrequests` on `redocly/cli`, `lycheeverse/lychee`,
`semgrep/semgrep` and the test stack's `node:22-alpine` in one afternoon, failing four jobs on a
clean branch (#1316). Logged in, pulls count against the account's own budget. The step reads two
repository secrets, `DOCKERHUB_USER` and `DOCKERHUB_TOKEN` (a read-only access token), and is
skipped where either is absent — a fork's pull request, or one Dependabot opens, which runs with
Dependabot's own secrets rather than the repository's unless the two are set there as well — so
such a run pulls anonymously, as every run did before; a token without a user would fail the
login rather than fall back, which is why both are required. Only whether both are set reaches
the job's environment, never the token. A pull the registry refuses all the same is named as
the environment's failure only where the gate runs through the runner (§ The tiers, the
registry's case): `npm run check`, which is what `Lint & Type Check` runs. The other four jobs
call their gate's script or the compose stack directly, so a refusal there still reads as the
job's own failure until its log is opened.

Inside the `check` job the setup steps have keys of their own: the root `npm ci`
is unconditional, because `lint:md` needs markdownlint from there and is the one
gate a prose-only change runs that needs an install at all; the backend and
frontend installs wait on `job_check_node` and the cv-python venv on
`job_check_python`. The job then runs `npm run check` unchanged, with
`GATES_BASE` set from the `Changes` job's own base, so the two cannot disagree
about what changed. The `security` job's Semgrep steps, `Semgrep SAST (Node)`
and `Semgrep SAST (Python)`, read `job_security_node` and `job_security_python`
separately: the Python scan is
pointed at `cv-python/` alone, so a backend change cannot alter its answer and
does not pay for it, while the Node scan is pointed at the whole checkout with
rule packs that carry Python rules, so `cv-python/` is one of its inputs and a
cv-python change pays for both. `trivy-image` no longer waits for `build`: it
builds the image it scans, and a cv-python-only change asks for no build at all.

The `e2e-smoke` job runs three lanes, because it is the one job in CI with a
database. The smoke step keeps the stack up when it is done
(`TEST_REPORT_KEEP_ENV=1`), and the step after it runs `npm run test:db` — the
database-backed backend specs (#522; which specs those are is
`docs/tech/development-guide.md` § Tests that need a database) — against that
same stack, keeping it up too. The third runs `npm run test:api`, the API
contract lane (§ The API contract), against the same backend; it reads
`job_test_api` and fails the job like the others. The database step reads `job_test_db`, a key of its own
in the shape of the `Semgrep SAST (Node)` and `Semgrep SAST (Python)` steps.
It holds only when `job_smoke` does, since the lane reads a subset of what the
smoke gate reads; what `scripts/gates.test.mjs` pins is that containment — a smoke
gate narrowed to fewer inputs than `test:db` reads would leave the step inside a
skipped job, reporting Success with nothing run.

A scheduled run (`on: schedule`, weekly) has no base, so the `Changes` job sends
the zero sha and every gate applies — see the calendar under *What the map does
not reach*.

A push to a pull request cancels the run on the head it replaced (#920). The
workflow's `concurrency` group is the pull request's number with
`cancel-in-progress` on, and for every other event — a push to `main`, the
weekly schedule, a dispatch — the group is the run's own id, so those always
finish. A shared group with cancellation off would not do: GitHub keeps one
*pending* run per group, so a third push to `main` would still replace a second
one that had not started. The review workflow cancels the same way, keyed on the
pull request, with its group on the `review` **job** rather than the workflow:
every comment on a pull request starts that workflow, and a job its `if:` skips
never joins the group — measured on a probe PR (#966) — so a thread reply or
the round's dispositions comment leaves a review in flight alone, where a
workflow-level group would have cancelled it.

The fail-safe invariant itself is pinned by `scripts/ci-failsafe.test.mjs`, which
parses the workflow and holds it against the map (#952). Every job but `Changes`
has to wait on it, and its `if:` has to be the whole expression — the clauses in
the order and the grouping above, built from the `job_*` output the map
publishes for that job. No job may wait on `check`, and the spec names the
measurement that took the waits out. The parts are not enough: an expression that names
every clause but puts the output comparison in an `&&` term of its own skips the
job on exactly the failure the fail-safe is for. Each guarded step's condition is
pinned whole the same way; `Changes` has to declare every `job_*` key the map
emits, and the workflow may read no key it does not; and `on:` has to carry no
`paths` filter. It reads in both directions: every job the map names has to exist
in the workflow, once, so that deleting a job takes the spec red rather than its
gates quietly out of CI.

Each failure says what the missing clause costs — a required context reporting
Success with nothing run on it — because that is the part a reader of the diff
cannot see. The spec runs in the backend's vitest lane, on the host and in the
container, which mounts that one workflow file read-only beside the repository
files the suite already reads.

### The job graph

Every job starts when `Changes` has decided whether it runs. No job waits on
another one, because a wait costs every run its length, and it pays off only on
a run where the job waited on would have failed (#965). The rule for putting a
wait back is the same as for taking one out: a measurement, recorded here, or
an artifact the waiting job consumes.

The measurement is `node scripts/ci-graph-measure.mjs`. It reads every
`pull_request` run of `ci.yml` in a window, with its jobs, through `gh api`,
and keeps what it read in `data/cache/ci-graph/`. Runner-minutes are the sum of
the jobs' own durations, not GitHub's billing, which rounds each job up to a
minute. The window below opens at the merge of #920, which made a push
cancel the run it superseded.

never incurred.

**The frontend is built twice per run, and stays that way.** `Build` runs
`vite build` on the runner: its *Build frontend* step took 11–16 s across 12
green runs on 2026-09-28. `Performance (Lighthouse)` runs `vite build` again,
inside the stack's frontend container in preview mode. In one run that day,
the container started and the frontend answered 22 s later, while Lighthouse
itself ran for 5.7 minutes. `E2E Smoke` browses the dev server and builds no
bundle. The two bundles are not the same file: `VITE_API_URL` and
`VITE_MARTIN_URL` are read at build time, and the one Lighthouse measures
carries the test stack's in-network hostnames. Sharing a build would mean
building it once with the stack's environment and mounting it into the preview
container. That couples a runner job to the stack's addresses to save about
fifteen seconds in a job that runs for eight minutes, so each lane keeps
building its own.

## The API contract

The OpenAPI document (`packages/shared/src/openapi.generated.json`, ADR-0072) is what a native
client is generated from, so a change to it can break a client that was built against the
previous one: a path removed, a response field removed or narrowed, a request field newly
required. `api:breaking` (`scripts/openapi-breaking.mjs`) asks that of every change to the
`api-contract` class:
- It takes the document at the merge base of the branch and its base: `--base` when the run
  was given one (the runner hands it to each gate as `GATES_BASE`), `GATES_BASE` in CI, and
  `main` on a machine. A review wave's `--base` is the pushed head; once a fold has rewritten
  the branch past it, that merge base is the fork from `main`, and the gate reports the
  branch's contract changes rather than only the wave's.
- It compares that document with the one in the tree using oasdiff, pinned by digest.
- It names each change oasdiff classes as breaking, and apart from those, each it classes as
  possibly breaking, such as a value added to an enum a client may switch over.
- In CI the count is a warning annotation on the run, and the full list goes to the job
  summary.
- A run with no base named at all (the zero sha CI sends on purpose for its weekly and dispatched
  runs) has no earlier contract to be asked about, and passes with one line saying so. A run whose
  named base has no merge base, as in a shallow checkout, never passes silently. It is annotated as not compared, and it earns what a
  break would under the policy. A base older than the document holds no contract to break and
  passes. That case is decided by `git ls-tree`, so an unreadable commit fails the check rather
  than reading as "no document".

**The policy is `warn` while no native client exists.** The web is built from the same commit as
the backend it calls, so a break it does not survive fails its own typecheck in the same pull
request. A native client does not ship with the backend: an installed app keeps calling the
contract it was built against for as long as it stays installed. When the first native client is
released, `POLICY` in the script becomes `fail`, and a deliberate break then needs one of two
things:
- a path kept and marked deprecated beside its replacement until the clients that call it are
  gone;
- a pull request that says in its description which client versions the break strands.

### The web client against the document

`api:client` (`frontend/scripts/api-client.mjs`) regenerates the web's API client from the
document with Orval (ADR-0073) and fails while the committed `frontend/src/api/client.generated.ts`
is not what that generates.
- Its inputs are `api-contract`, `shared`, which the document's own path belongs to, `web`,
  which holds the mutator and the Orval configuration, and `node-deps`, since an Orval
  upgrade changes the output as surely as a route does.
- A changed route therefore asks for two regenerations in turn: `npm --prefix backend run
  api:openapi` for the document (`openApi.test.ts` holds it), then `npm --prefix frontend run
  api:client` for the client.
- Orval writes the mutator's import relative to the file it writes, so the check generates beside
  the committed file under a scratch name, compares the two, and removes the scratch file.
- What the client buys is checked by the typecheck, not by this gate: a request the document does
  not describe fails `typecheck:frontend` in any module that calls through the client
  (`frontend/src/api/apiFetch.test.ts` pins that with `@ts-expect-error`).

### The running API against the document

`npm run test:api` (`scripts/test-stack.sh run-api-contract`, `scripts/api-contract.mjs`, #1091)
holds the running backend to the document. Schemathesis, pinned by digest, generates requests from
the document, valid ones and deliberately invalid ones, and fails on:
- an undocumented 500;
- a response that does not match its schema, or a content type the document does not name;
- a valid request refused, or an invalid one accepted;
- a route that answers without the token its access declares.

It runs against the isolated test stack's backend and refuses any other address, the dev
backend's port included:
- **Four callers.** It runs once anonymously over the `public` and `optional` routes, then as the
  fixture's traveller, curator and admin over `signed-in`, `curator` and `admin`. The fixture seeds
  those accounts only into a database whose name says `test`, and their credentials are read from
  the fixture module rather than restated.
- **Reads only.** The stack is shared with the smoke and database lanes, and a write would change
  what they read. The GET routes that start long work or call a service outside the stack (OAuth
  redirects, Nominatim, Wikidata, Wikimedia, OpenAI, the geometry and colour-match streams, the
  catalogue checks) are left out by name, each with its reason, in `EXCLUDED`.
  `scripts/api-contract.test.mjs` fails on a name the document no longer has.
- **One check left out.** `unsupported_method` expects 405 for a method a path does not declare.
  Express answers 404, and a 405 with its `Allow` header is a behaviour to decide on its own.

What the lane holds the API to includes three answers that are not a 500:
- an id past a Postgres `integer` is refused at the boundary, every id being bounded in
  `types/rowId.ts`;
- a NUL byte in text is a 400;
- Sign in with a provider the server has no credentials for is a 404.

The traveller's run keeps under `authenticatedLimiter`, which, unlike the read limits, the
environment cannot raise, so its probes meet the 401 they look for rather than a 429. A query
parameter a route does not declare is refused with 400 (#1099, `development-guide.md` § API Layer),
so the lane's findings are defects and its step fails the job.

## What the map does not reach

- **The calendar.** Trivy, `npm audit` and `pip-audit` answer from vulnerability
  databases, so their verdict changes when a CVE is published, not when a file
  moves — before #783 every push re-asked them, and under the map alone a
  base-image CVE disclosed after the last `cv-python/` change would be found by
  nothing (Dependabot alerts cover the manifests; the image's OS packages have no
  such backstop). The map cannot name time as an input, so `ci.yml` supplies it:
  a weekly `schedule:` trigger, which carries no base and therefore runs every
  gate.
- **The `docs` class is `*.md`, while `lint:links` resolves links to any file.**
  Renaming a `.sh`, an `.sql` or an image leaves a dead link in prose that this
  map does not chase, because the change touched no Markdown. The next docs edit
  finds it, or a CI run after a change to the map or the workflow, which runs
  every gate.
- **A workflow's syntax is read; what it needs from GitHub is not.** The gap ADR-0062
  recorded here — the Claude workflows in no input class, `ci.yml` held
  only to the fail-safe contract and never to the syntax of a workflow file — is
  closed: `lint:actions` runs actionlint over the `workflows` class, which is
  `.github/workflows/` whole (#951). It parses each file, type-checks the `${{ }}`
  expressions against the outputs and contexts actually available, checks a `uses:`
  step's inputs against the action's own, and runs shellcheck over every `run:`
  block. What it cannot see is the half that lives outside the file: whether a
  secret, a variable, a permission or an environment the workflow names exists in
  this repository's settings, and whether a job does what it says. An unset secret
  is not an error but the empty string, so neither this gate nor GitHub's own parser
  says a word: the cost lands later, on the step that needed a real value — or it
  never announces itself at all, an `if:` on that secret simply reading false and
  the step quietly not running. The fail-safe contract likewise remains the business
  of `scripts/ci-failsafe.test.mjs`.
  The gate finds its own files rather than being handed a list, so a workflow added
  and not yet tracked is linted too; a discovery that turns up no project or no YAML
  under `.github/workflows/` exits 3 rather than 0, which is what keeps the gate from
  going quiet if the directory ever moves.
  ADR-0062 records the gap as it stood when it was accepted, before either existed.
- **`job_check_docs` is emitted and nothing reads it.** The install the docs
  gates need is the unconditional root `npm ci`, and the Docker gates install
  nothing. The key is still published on every run, because a `job_*` key that
  appeared only sometimes would reach an `if:` as the empty string and read as
  false — and because the next docs gate may well need a setup step of its own.
- **No gate covers the backend ↔ cv-python HTTP contract.**
  `backend/src/services/cv/pythonCvClient.ts` calls the FastAPI service over
  HTTP; no backend spec exercises it, and `scripts/test-stack.sh` starts `db`,
  `backend`, `frontend` and `martin` only, so cv-python is not in the smoke
  stack either. That was true before this map and is true after it — which is
  why `python` is not an input to the smoke lane: the lane cannot see it.

## Adding a gate

1. Add it to `GATES` in `scripts/gates.mjs`, naming its `tier`, its `inputs`,
   the `command` a person would type, the CI `job` it belongs to and the
   `setup` its runner needs. If it reads a kind of file no class covers yet, add
   the class to `INPUTS` with the sentence that says why those paths and no
   others — that column is the argument, not a label.
2. Run `node scripts/gates.mjs --table` and paste both tables into **The map**
   above, replacing what is there. `scripts/gates.test.mjs` asserts this document
   contains the generated text verbatim, so `npm test` is red until it does.
3. If the gate is a new CI job, add its key to `githubOutputs()` and give the job
   the `if:` shape above; if it is a step inside an existing job, give the step
   its own key the way `Semgrep SAST (Node)` and `Semgrep SAST (Python)` have theirs.
4. Check the verdict on a change that should skip it and on one that should not.
   A gate whose inputs are wrong fails the way this whole file exists to prevent:
   quietly, by not running.
