# ADR-0073: The web client is generated from the OpenAPI document by Orval

**Date:** 2026-09-27
**Status:** Accepted — decisions 4 and 5 narrowed by ADR-0074
**Issue:** [#1101](https://github.com/uncovering-world/track-your-regions/issues/1101), a slice of [#1089](https://github.com/uncovering-world/track-your-regions/issues/1089)

---

## Context

The web client builds every request by hand. Each function in `frontend/src/api/` spells:
- its URL, as in `` `${API_URL}/api/experiences/review/answer` ``;
- its method;
- its query string, through `URLSearchParams`;
- its body.

The compiler checks none of them against the backend. Only the answers are typed from it, through the types ADR-0066 renders into `@tyr/shared/api`. The web's own guard on the paths is `backend/src/routes/adminClientPaths.test.ts`. It reads the admin client modules with regular expressions, and covers `/api/admin` alone.

Since ADR-0072, the OpenAPI 3.1 document (`packages/shared/src/openapi.generated.json`) states every route's path, method, parameters, request body and answers. Redocly lints it, oasdiff compares it with its base, and Schemathesis tests the running API against it (#1091). #1089 asks for a web client generated from it, and for a rule on how that relates to ADR-0066's answer types.

The Epic named `openapi-typescript` with `openapi-fetch`. On 2025-12-29 their maintainers put `openapi-fetch` and `openapi-react-query` into maintenance mode: they "won't get future updates" ([2026 roadmap](https://github.com/openapi-ts/openapi-typescript/discussions/2559)). Neither package has shipped since 2026-02-11 (npm), and `openapi-typescript` declares `typescript ^5.x` as a peer. This project takes a maintained library over a hand-written layer, and over a library that has been frozen.

The candidates were measured against this repository's document on 2026-09-27: 220 paths and 450 components.
- **What the document uses:**
  - 137 `["string", "null"]` type arrays and 8 `prefixItems` tuples (`AnchorPoint`, `FocusBbox`);
  - six 204 answers, and two geometry reads that answer 200 or 204;
  - three `text/event-stream` answers and four `image/*` answers.
- **Orval 8.38.0**, with the `fetch` client and a mutator:
  - it generated the client in 2.6 s, and the result type-checks under `strict`;
  - a 200-or-204 read is typed `DivisionGeometry | void`, a 204-only call `void`, and an image `Blob`;
  - `ReviewAnswerBody` and `GetExperiencesReviewQueueParams` are typed from the document;
  - 360 of the 361 answer types `@tyr/shared/api` renders exist as Orval models under the same name, and all 360 are mutually assignable with ours. A deliberately altered type fails the same check. The one missing, `ExperienceLocation`, is a schema no route answers directly, so the document inlines it where `RegionExperienceLocation` extends it.

## Decision

1. **Orval generates the web client from the OpenAPI document.**
   - Orval is a devDependency of `frontend/`, pinned to an exact version.
   - It uses its `fetch` client: plain async functions, one per operation, over the browser's `fetch`. Each function takes the path parameters, the query parameters and the body as typed arguments, and returns the typed answer.
   - The generated code imports nothing at run time but the mutator (decision 2), so the bundle carries only the functions the web calls.
   - The output is committed under one generated directory in `frontend/src/api/` and regenerated by one command. A gate on the `api-contract` input class (ADR-0062) fails while the committed client is not what the committed document generates, the way `openApi.test.ts` holds the document.
2. **The token handling is the mutator, and stays ours.** Orval calls one function we own for every request: the mutator. It carries what `authFetchJson` (`frontend/src/api/fetchUtils.ts`) does today:
   - the in-memory access token;
   - `ensureFreshToken` before a call;
   - one retry after the deduplicated `refreshSession` on a 401, and `auth:session-expired` when the refresh fails;
   - `credentials: 'include'`;
   - the error thrown with the server's `error` sentence.

   It reads the answer by its content type: JSON as JSON, an image as a `Blob`, and a 204 as `undefined`, which the types already say may come.

   The mutator's options extend `RequestInit` with one of our own: the call's **token policy**. The policy covers the whole exchange, both the step before the request and the answer to a 401, because a call that differs in one differs in both.
   - **`session`, the default:** everything listed above.
   - **`strict`:** `requireFreshToken()` before the request.
     - A spent token fires `auth:session-expired` and throws the session-expired sentence without sending anything.
     - A 401 is the endpoint's own answer, and nothing is refreshed.
     - `changePassword` uses it: its 401 means a wrong current password, and a dead session must not read as one (`docs/tech/authentication.md` § Password Security).
   - **`as-held`:** the in-memory token is sent as it stands, when one is held, and is never freshened. A 401 is the endpoint's own answer, and nothing is refreshed.
     - Every `/api/auth` call that needs no session uses it: login, registration, email verification and its resend, and the code exchange.
     - So does logout. It must send the token it is ending, because the server blacklists the access token only when the request carries it (`docs/tech/authentication.md` § Token Lifecycle, "Logout Blacklist", and #1110). It must not freshen that token first, because a refresh would rotate the cookie it is about to revoke.

   A caller's own `Authorization` header wins over the in-memory token. `getCurrentUser` needs this: the OAuth flow calls it with the token it has just received, before that token is the in-memory one.

   `refreshSession()` itself stays a plain `fetch` outside the generated client. It owns the deduplication the mutator relies on, and routing it through the mutator would have the mutator refresh in order to refresh.

   With those policies, the hand-built calls `CLAUDE.md` § Structure notes records as exceptions or as debt move to the generated client, `refreshSession()` apart.
3. **The generated functions are plain calls, and the query keys stay in `queryKeys.ts`.**
   - Orval's TanStack Query hooks are not generated. Their keys would be a second owner of the keys that `frontend/src/api/queryKeys.ts` states once (#790).
   - The client modules in `frontend/src/api/` keep their exported, domain-named functions for the hooks and components that call them, and each one's body becomes a generated call.
4. **The answer types move to the document when the last client module has moved.**
   - The generated models are the types `@tyr/shared/api` renders today, under the same names. ADR-0066's renderer (`backend/src/api/apiTypesRender.ts`, `api:types`, `apiTypes.test.ts`) is then a second path from the same schemas to the same types. #1108 deletes it and `packages/shared/src/api.generated.ts`, and the web imports its answer types from the generated models.
   - Before that, a type the web names that the document inlines, like `ExperienceLocation` today, is made a named component: the backend's generator names components from exported schemas (ADR-0072 decision 2), so no hand-written type stands in for it.
   - Until #1108, both paths exist and describe the same types.
5. **Every API route's URL comes from the document, whatever reads it.** Orval exports a URL builder for each operation (`getGet…Url`) beside its function, so the transport decides which one a call uses:
   - **Every request the web makes with `fetch` goes through the mutator, so there is one token path.**
     - A route read by a generated function is answered by the mutator, an image as a `Blob`. That covers the `image-proxy` fetches in `useImageColorPicker.ts` and `ImageOverlayDialog.tsx`.
     - `authFetchBlob` goes. Where a component holds an image route's URL rather than a call, `AuthImage` for the cluster preview and the water crops and the cluster highlight in `CvClusterReviewSection.tsx`, it reads that URL through the mutator.
   - **A URL the browser fetches by itself keeps that transport and is built with the generated builder.** That covers:
     - the server-sent streams opened with `EventSource`: the compute stream, the colour match and the coverage;
     - the token-query image URLs an element loads directly (`wvImportCvMatch.ts`);
     - the OAuth start routes, which are navigations.
   - **The Martin tile URLs are not API routes and stay as they are:** Martin serves them, and the document does not describe them.

## Alternatives Considered

| Option | Why rejected |
|--------|-------------|
| `openapi-typescript` + `openapi-fetch` (the Epic's proposal) | Its maintainers put `openapi-fetch` into maintenance mode on 2025-12-29, with no future updates; no release since 2026-02-11, and a `typescript ^5.x` peer. Its types are as good as Orval's (the same 360 names match), but the call layer would be a frozen package. |
| `openapi-typescript` for the types and a call layer written here | Writes by hand what a maintained generator does: URL building, query serialisation, per-operation typing. Every one of those is a place a drift hides, and preventing drift is the point. |
| `@hey-api/openapi-ts` | Pre-1.0 (0.99.0), with no stable release since 2026-06-22, and 644 open issues and pull requests. On our document it renames the 13 `AI…` types (`AIModel` → `AiModel`), so decision 4 would become a rename across the web. |
| Orval with its TanStack Query hooks | Generates query keys of its own shape. `queryKeys.ts` is the one owner of keys, with a lint that refuses literal keys (#790); a second owner is what that slice removed. |
| `openapi-zod-client`, `@zodios/core` | Unmaintained. The first is deprecated in its own README in favour of `typed-openapi`, and its last release was 2025-02. The second's last release was 2023-08, on Zod 3 and axios. |
| Keep the hand-built calls | The drift this Epic exists for: a path, a parameter or a body field the backend no longer takes compiles, and answers 404 or 400 only when someone presses the button. |

## Consequences

**Positive:**
- A misspelled path, a missing path parameter, a wrong query parameter or a wrong body field fails to compile, on every route rather than on `/api/admin` alone. `adminClientPaths.test.ts` and its regular expressions go in #1108.
- The request types come from the backend's schemas, so a request type declared by hand in the web goes away.
- The web and the planned native clients read one contract: the document that is linted, compared for breaks and tested against the running API.
- The token handling stays one function we own. A call whose token differs, such as `changePassword`'s strict one, a pre-auth call's or logout's as-held one, or `getCurrentUser`'s own, names its policy instead of being hand-built.

**Negative / Trade-offs:**
- **A code generator in the toolchain.** Orval has 25 direct dependencies, among them its own packages for other frameworks. It is a devDependency only; the generated code has none, and the pin plus `npm audit` (the `security:deps` gate) cover the install.
- **Committed generated code.** It is many thousands of lines, about 8,300 for the functions alone. The pilot puts it in one directory and counts that directory as generated for the review surface.
- **Two paths to the same answer types until #1108.** Mutual assignability holds today, and the migration slices import from one of them, not both.
- **A 204 becomes `undefined`.** `authFetchJson` reads a 204 as `[]`, and a caller that relied on that must now handle `void`, as the types say. That is the confusion `authFetchOptionalJson` was written for, and it now ends at the compiler.
